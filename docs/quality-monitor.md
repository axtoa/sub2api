# Best AI 质量监控

入口：管理员侧边栏「仪表盘」下方的「质量监控」。普通用户无法访问页面或 API。

## 第一版的边界

- 首次进入自动同步全部未删除账号；后续刷新只更新检测结果，新增账号通过「同步账号」手动补入。停用监控或暂不支持检测的账号仍展示，删除的账号不展示。
- 一个账号一张卡片，多个模型在卡片或详情中切换，多分组账号不会重复计数。「紧凑 / 标准」只改变信息密度，选择保存在本机，不修改检测设置。
- 同步只读取本地模型映射中的具体文本模型；没有映射时使用项目现有的平台默认测试模型。不会扫描上游模型接口；通配符、媒体模型和不支持的类型不会自动发送检测。可在账号详情的「单独设置」中增加具体模型。
- 重复同步只补充账号与模型，不重置关闭状态、独立配置、历史或频次。旧版本全部模型都关闭的账号，首次同步时保留账号关闭状态。
- 支持 OpenAI API Key / OAuth、Anthropic API Key / OAuth / setup-token 文本账号。暂不支持 Gemini、媒体模型、通配符目标、凭据影子和需要创建远端任务的 Agent Identity 账号。
- 复用账号测试的认证、代理、模型映射和协议选择，固定账号，不经过故障转移。质量检测专用上下文禁止原有测试接口的错误状态、429 状态和额度快照写入。
- **只观察，不自动禁用或恢复账号，不调整优先级、分组、价格和用户账单。** 实际请求会消耗上游额度；检测预算独立记录，不写用户消费日志。
- 能力检查采用随机参数的路径计数、条件记录统计、异或约束题，本地生成标准答案并判题。不调用付费裁判模型，不执行回答中的代码。
- 单轮未达门槛显示「疑似异常」；上一轮相同配置也未达门槛时显示「持续异常」。这只是小样本任务表现，**不能证明模型身份，也不能保证识别所有能力降级**。建议先以可信正常账号校准，再看相同模型、参数的历史变化。
- 超时、截断、限流、预算不足和请求参数被拒绝记为未完成，不判答错。历史保留参数标识、题目、标准答案、回答、实际报告模型、用量和原因。

## 默认频次与成本

| 项目 | 默认值 | 请求数 |
| --- | --- | --- |
| 补充测活 | 每 60 分钟 | 每轮 1 次；近 15 分钟有真实成功且无采集到的上游错误则跳过 |
| 能力检查 | 每 12 小时 | 每轮 3 题，每题 1 次 |
| 缓存验证 | 仅手动 | 每轮 2–3 次，32 KB 稳定前缀；后续请求换问题后缀 |
| 异常复测 | 追加 1 轮，间隔 5 分钟 | 受同一预算约束 |
| 输出上限 | 每次 2048 token | 可在 256–8192 之间调整 |
| 每日预算 | 1000 次请求、200 万 token | 按服务端配置时区零点换日 |

以上均可在「检测设置」修改；每个账号模型也可「单独设置」，或恢复继承全局值。全局、账号、模型的自动检测开关只影响自动任务。手动检测不受自动开关、自动频次、自动预算和账号调度冷却限制，但仍需真实管理员鉴权、受支持的账号类型、并发槽和请求超时。已经发往上游的请求无法撤回。

默认单目标最多约 30 次常规请求/日（24 次测活 + 6 次能力题，不含复测），真实调用会减少补充测活。模型推理成本、缓存验证的长输入成本不能只看请求数。页面显示每日计划估算和实际预算占用，不承诺固定人民币成本。

每次请求先以 UTF-8 字节上界、系统提示、最大输出及额外开销预留 token，再根据完整上游报告结算；用量缺失、格式不合法、响应中断或进程崩溃会保留保守预留量，不按零消耗处理。上游实际超报仍会计入，因此预算是保守调度阀门，而不是第三方账单的绝对封顶承诺。降低预算不清空已用量。手动请求和 token 单独统计，不扣自动预算，没有自动预算上限保护，请自行控制手动检测次数。

## 缓存与可用性口径

- 卡片缓存比例仅采用主动验证的上游报告值，不采用站内 usage_logs 的计费缓存调整。
- 主动「缓存验证」直接读取上游原始缓存字段。预热后的请求报告缓存读取大于零才显示「观察到命中」。
- 完整回答但未命中显示「未观察到命中」；没有缓存字段显示「无法判断」。缓存写入传播时间、模型缓存门槛、路由以及上游不透传字段均可能影响结果，不能据此认定缓存故障。
- 缓存输入占比为验证请求的缓存读取 token / 输入 token，预热请求不计入。Anthropic 分母包含非缓存输入、缓存读取及写入；OpenAI 分母为上游报告的总输入。用量字段缺失或不一致不显示为 0% 或 100%。
- 真实调用失败数来自运维上游错误日志，受日志开关、采样和保留范围影响，不视为完整请求成功率。近期可用性条仅记录检测任务（含明确标记的真实流量跳过），不伪造流量。
- 24h 探测可用率使用最近 24 小时已完成可用性检测的成功 /（成功 + 失败），未知和未完成不计入分母；没有有效记录显示「—」。探测条最多 180 次，不足的格子留灰。
- 能力详情展示精确题目、本地标准答案与解法、原始回答、判定、请求参数及上游报告模型。原始回答仅按文本渲染，不能执行代码；上游自报模型不是身份验证。

## 持久化与升级

- 迁移 `244_quality_monitor.sql` 与 `245_quality_monitor_accounts.sql` 仅新增或调整 `quality_monitor_*` 表及索引，不改原账号、用量和订单数据。
- 队列持久化。自动任务去重，手动每次点击都生成独立任务，不因已有排队任务被丢弃；同一账号模型同时最多一个执行任务，跨进程锁保护抢占。每进程串行执行，手动队列优先；自动并发满跳过，手动等待可用并发槽至请求超时，不突破业务并发上限。
- 手动任务不改自动计划的下次执行时间，也不追加自动复测。修改检测题目或请求参数会停止当前轮；单纯调整自动开关、预算和频次不影响已受理的手动任务（频次不参与实际题目或请求参数变化时）。
- 服务重启后过期执行任务标为「执行中断」，不自动重放可能已经扣费的请求。完成时使用版本校验，旧任务不能覆盖新设置的调度时间；每条请求前复核目标、设置和账号路径。
- 最近 24 小时的已完成检测全部保留，保证 24h 探测可用率的分母完整；更早的历史只保留每目标每类型最近 180 轮，且不超过 30 天，按小时分批清理。卡片最多返回 180 条探测格。生成的参考答案只在请求完成后保存在本站，不发给上游。
- 上线无需配置新依赖；上线前仍应执行数据库备份，并用小范围账号观察默认门槛。回滚旧程序时保留新增表即可，勿删除业务表。
