# 站内 CDK 商城实施方案

日期：2026-11-01。状态：设计稿，业务功能尚未实施。

## 1. 已确定的业务边界

本站是轻量商城：商品展示、显示库存、收款、交付供应商 CDK、提供兑换跳转。
用户在 `https://cdk.aisale.best/recharge` 兑换 CDK，兑换后的代充、进度和完成结果由该系统负责。
本站订单记录到“已发码”，不能把发码、点击兑换按钮或用户离开页面认定为“代充成功”。

- 商城使用 `/shop`，商品公开浏览；登录用户和访客都能付款购买。登录用户订单关联本站用户 ID，访客订单使用订单恢复凭证/邮箱核验找回。
- 后台所有业务入口集中在“代购管理”，继续使用原管理员权限。
- 管理员提前按商品导入供应商 CDK，不额外生成一套站内兑换码。
- 第一期每笔订单购买一份商品、交付一枚 CDK，不做购物车和混合商品结算。
- 第一期开通当前已经验证可用的易支付支付宝方式，不自动开放其他支付方式。
- 商品以人民币分保存售价，展示人民币，不应用中转充值倍率、赠送比例或订阅汇率。
- 不建设代购钱包，不接受中转余额支付，不调用中转充值兑换接口。登录用户可按商品配置生成一条“待人工发放”的中转余额奖励记录；商城不自动写入或调用中转余额接口。访客购买不产生可发放的余额奖励。
- 不接供应商自动代充 API，不收集代充账号密码或会话，不查询外站兑换进度。

## 2. 当前代码提供了什么

现有 `backend/internal/shop` 已经拥有独立商品和人工代购订单，前端位于 `frontend/src/features/shop`。
目前用户商城仍使用中转的 `AppLayout`，购买流程是外部付款链接和人工确认，不能直接视为自动发码商城。

现有易支付实现可作为协议行为的参考，但商城服务不能直接调用中转的支付服务、provider registry 或共用可变对象。
为防止未来共享适配器改动影响充值，商城服务需有自己的 EasyPay 客户端实现、配置和回归契约测试；调用自己的回调/返回地址。

需要特别注意三处：

1. `backend/internal/service/payment_fulfillment.go` 的 `executeFulfillment` 将订阅以外的支付订单交给余额充值。不能将商城订单直接塞进这个流程。
2. `backend/internal/service/payment_config_providers.go` 的待处理订单保护只查询中转 `PaymentOrder`。直接引用同一条可变渠道配置，会让商城未完成订单不在原保护范围内。
3. 现有支付配置保存逻辑实际写入 JSON，部分历史加密接口已废弃。不能因函数名带有 `encrypt` 就声称新商城密钥已经加密。

## 3. 前台与运营后台

### 用户商城

- `/shop`：独立商城布局，展示商品、售价、可售库存，售罄时禁止购买。
- `/shop/products/:id`：规格、使用条件、商品说明、兑换教程和购买按钮。
- `/shop/orders`：已登录用户的购买记录；访客可通过订单恢复入口查找自己的订单。
- `/shop/orders/:id`：付款信息、支付状态，以及付款交付后的 CDK、复制按钮、前往兑换按钮。
- 顶部提供商品、我的订单、登录/账户和返回中转控制台，不展示中转侧边栏和账户余额。
- 登录购买关联用户 ID；访客购买通过短时高熵恢复凭证或邮箱验证码恢复订单，不要求创建账号。
- 兑换按钮打开固定 HTTPS 兑换地址，不自动把本站令牌、用户信息或 CDK 拼到网址中。

CDK 使用独立的受权限保护的领取接口返回。公开商品、订单列表、支付状态轮询不携带完整 CDK。
本人领取及管理员授权查看都需校验权限，响应禁止缓存，访问记录不包含明文 CDK。

### 代购管理

| 页面 | 主要功能 |
| --- | --- |
| 商品管理 | 名称、规格、图片、人民币售价、说明、兑换教程、上架和排序 |
| CDK 库存 | 按商品批量导入、去重、批次和成本、可售/预留/已售/停用数量、低库存提醒 |
| 销售订单 | 商品与售价快照、支付流水、发码状态、人工核实、退款和交付重试 |
| 人工奖励 | 仅展示已付款登录用户的待发余额奖励、金额、所属账号、人工发放状态和操作审计；不提供自动入账按钮 |
| 支付设置 | 商城独立启停、易支付商户参数、允许方式、付款期限、配置版本 |
| 商城与首页设置 | 商城名称、客服、首页入口和推荐商品、暂停新销售 |

库存导入提交前显示有效数、重复数、无效数。第一期采用整批校验通过后再入库，避免静默部分成功。
重复检测覆盖数据库内已售和停用的码，不能把已售码重新导入。只去掉码首尾空白，不擅自变更大小写。
原始 CDK 加密保存，另存不可逆指纹用于唯一性检查。列表默认遮挡，不提供普通用户批量导出。
管理员可以停用未售出的码；已预留的码先处理对应订单，已售记录保留，不物理删除。

## 4. 支付隔离方案

### 共享边界一览

| 能力/数据 | 是否共享 | 边界 |
| --- | --- | --- |
| 用户账号与登录身份 | 是 | 共用账号体系；经中转认证服务兑换商城专用短时令牌，商城获得稳定 user ID，不读写中转用户表或认证数据 |
| 管理员身份 | 是 | 管理员可用同一身份登录；认证服务签发商城 audience 的管理员权限声明，商城权限不能提升中转权限 |
| 易支付商户账户 | 是 | 同一个外部商户可收两边款；这是外部共享依赖 |
| 易支付协议 | 仅协议层相同 | 两边各自实现和运行支付客户端；不共用运行时对象、registry、订单处理或回调代码 |
| 商户密钥 | 配置值分别保存 | 管理员分别录入；商城与中转各自保存配置副本，轮换时分别更新，任何服务不能读取另一边的密钥存储 |
| 支付订单、交易号、退款记录 | 否 | 分别写入各自数据库；通过各自回调、服务端查单与对账 |
| 商品、CDK、代购订单和售后 | 否 | 只属于商城专属数据库，中转无权访问 |
| 中转余额、订阅、充值码、用量 | 否 | 中转余额由管理员手动发放；商城只保存独立奖励待办记录，没有余额 API、数据库权限或自动履约代码 |
| 前端静态资源、通用品牌和跳转链接 | 可以 | 可复用展示资源；资源加载故障不能成为中转支付后端的依赖 |
| 日志/监控平台 | 可以有限共用 | 仅传递脱敏日志、独立 service 标签、指标和告警；CDK、密钥、支付签名不得写入 |
| 数据库、队列、进程和连接池 | 否 | 独立部署和资源限额，避免商城流量或故障占满中转容量 |

因此，“共用用户和支付”准确含义是共用账号身份，以及共用外部易支付商户账户/协议；不是共用用户表、支付服务、支付单或回调实现。
唯一不可避免的运营联动是同一易支付商户的可用性、限额和密钥有效性；独立数据库及支付进程可以避免商城代码误改中转订单或充值逻辑，但不能隔离支付平台或商户本身的故障。

### 4.1 共用商户账户，不共用可变业务配置

同一个易支付商户可以同时接中转和商城，钱仍进入同一收款账户。站内销售记录和收入统计分别计算。

管理员可从已验证的商户参数初始化商城专用配置，但之后两条业务线不共享配置记录，也不相互读取对方运行时配置。
商城服务使用自己的加密配置和版本快照。初始化通过受限管理接口显式完成，不允许商城进程读取中转支付实例表或解密其密钥。

- 管理员在商城专属配置中单独录入当前正在使用的商户地址、商户 ID、密钥及允许的支付宝子渠道。前台用户仍只看到支付宝，不新增支付方式选项；后台有独立的商城启停开关。
- 密钥只写入商城配置存储，不经前端回传，后台只显示已配置状态，不返回秘密值；日志和错误信息不包含密钥。
- 商城配置只含商户连接信息、支付宝子渠道、商城回调与返回基址、配置版本；不包含充值倍率、订阅换算、原回调或原返回地址。
- 原渠道的编辑、删除和停用，不自动改动商城配置；商城配置的编辑和停用也不写回原渠道。
- 不把商城配置注册到中转的全局支付 registry 或负载均衡列表，避免改变中转选路和回调兜底行为。
- 商城配置更新创建新版本，新订单使用新版本，旧订单继续绑定原版本；停用只阻止新下单。
- 旧配置在待处理、可退款或对账中的订单仍需要时保留，不允许硬删除导致无法验签或查单。

同商户仍有外部关联：在易支付平台重置商户密钥、封停账户、修改结算或触及平台限额，会同时影响两边。
配置副本不能屏蔽商户侧变化。密钥轮换需要安排两边及在途订单的过渡；若要连商户风险都隔离，必须使用独立商户。

### 4.2 独立服务、下单、回调和交付

若要求“商城出错也不能拖垮中转”，CDK 销售和支付应运行在独立进程/容器，而不是只在原 Go 服务中增加 package。
独立服务拥有独立部署、健康检查、并发/CPU/内存/连接池上限和熔断开关；商城崩溃、发布或队列阻塞不重启、不占满中转服务资源。
商城服务实现自己的 EasyPay HTTP 客户端与签名验签，仅复用公开协议和标准库/通用密码学原语，不导入中转 `PaymentService`、全局 `payment.Registry`、充值履约服务或共享易支付 provider 实例。
现有中转代码、回调和配置不作商城功能修改。两套实现通过同一组独立维护的易支付协议兼容测试验证。

商城 API 使用单独路径，例如 `/api/v1/cdkshop/*`，由边缘路由将该前缀转发到商城服务；原 `/api/v1/payment/*` 和 `/api/v1/payment/webhook/easypay` 路由保持原样。
商城自己的 webhook 直接路由到商城服务。它只查询商城支付表，未知商城单号不能进入中转回调处理；中转 webhook 也不查询商城表。
当前项目的普通 access token 使用 HS256，验证过程还会读取用户记录及 TokenVersion。不能把现有 HMAC 密钥交给商城服务：任何持有共享 HMAC 密钥的服务都能伪造中转可接受的令牌。
共用登录通过认证服务令牌交换完成：浏览器用现有登录态调用中转认证端点；认证端点按现有逻辑验证账号状态、token version 和管理员身份后，签发仅供商城使用、短时有效且带有固定 `iss`、`aud=cdkshop`、`sub`、最小权限和过期时间的身份令牌。
签发使用商城专用非对称密钥对；私钥仅留在认证服务/密钥管理系统，商城服务仅配置公钥并严格校验签名算法、issuer、audience、有效期及必要的权限声明。不得接受普通中转 access token、缺少 audience 的 token 或由商城自行签发的 token。
商城不获得中转 JWT HMAC secret、刷新令牌、数据库凭据或中转服务内部密钥。短时令牌到期后前端在用户原有登录态下静默换取，因此用户通常无需二次登录；中央认证服务不可用时，商城的新 API 请求会暂时无法认证，但不影响已创建订单的回调、支付处理或中转服务运行。
商城服务的数据读写接口不得被反向代理成中转余额、订阅或兑换码操作。

| 项目 | 中转充值/订阅 | 新 CDK 商城 |
| --- | --- | --- |
| 业务入口 | 原 `/purchase` | `/shop` |
| 支付接口 | 原 `/api/v1/payment/*` | 独立服务 `/api/v1/cdkshop/*` |
| 支付记录 | 原 `payment_orders` | 商城专属数据库中的 `cdkshop_payments` |
| 商户订单号 | 原规则 | 新独立前缀，例如 `SCDK...` |
| 回调 | 原 `/api/v1/payment/webhook/easypay` | 新 `/api/v1/cdkshop/payment/webhook/easypay` |
| 浏览器返回 | 原充值/订阅返回流程 | 商城自己的订单详情 |
| 收款后动作 | 原余额充值或订阅开通 | 将 CDK 绑定给商城订单 |
| 退款后动作 | 原充值/订阅退款规则 | 更新商城退款记录，不扣中转权益 |

商城 webhook 只在独立商城服务注册为公开路由，只凭合法支付签名确认，不要求用户 JWT；其他销售接口保留登录、管理员和限流保护。
回调 URL、返回 URL 均由可信站点配置生成，不能由用户提交，也不能在缺失时回退到中转地址。
公网支付平台无法访问 `127.0.0.1`，本地模拟和正式公网回调测试应分开进行。

回调订单号只能用于定位商城支付单及其配置版本，不能据此直接信任通知。验签后还要核对商户、状态、金额、交易号和订单归属。
商城不会把未知订单回退到充值接口。即使通知打错入口，也必须验证另一类订单的余额、订阅、库存都不会变化。
临时数据库失败返回可重试错误；已持久化的合法重复通知按易支付协议返回成功。未知订单分类记录，不记录签名、密钥或整段敏感报文。

### 4.3 数据、配置与故障隔离

要满足“不因商城代码失误影响中转”的目标，商城使用独立进程/容器、独立数据库实例、独立网络策略和独立凭据，不把“同集群不同 schema”当作最终隔离方案。
商城数据库账号只属于商城数据库，无权连接中转生产库；中转数据库账号也无权连接商城数据库。商城通过商城 audience 身份令牌的 `sub` 取得用户 ID，不查询或修改中转 `users` 表，也不持有中转 JWT HMAC secret 或令牌签发私钥。
CDK 和商户密钥分别使用商城专用认证加密密钥，密钥通过部署密钥管理注入，不能与 TOTP 或中转支付密钥混用。数据库备份与密钥备份分开控制。

商城网络调用设置超时、限流和有限重试；查单、补发任务限制并发和批次大小。商城服务数据库连接池、进程资源和队列设硬上限，边缘代理限流并提供商城独立熔断/暂停。
默认商品/API 读失败只影响商城页面；商城支付、数据库或后台任务故障不改变中转路由和中转健康检查。
商城部署在独立资源配额中，数据库、连接、CPU、内存、队列和网络并发均有限额；商城资源耗尽时由商城熔断，不占用中转资源。同一易支付商户的账户、平台限额和商户密钥仍是明确接受的外部共享点。

## 5. 数据结构及约束

新 CDK 商城使用自己的商品目录和独立、结构化的数据表，不复用现有人工代购的 `shop_products`/`shop_orders`；旧人工订单继续由旧模块读取和管理。
运营界面可以整合在“代购管理”入口下，但商品、库存、支付和销售请求均由独立 CDK 服务写入其专属数据库。

| 数据表 | 负责内容 |
| --- | --- |
| `cdkshop_products` | 商城商品、人民币售价、展示文案、上下架与版本 |
| `cdkshop_sales` | CDK 销售订单、用户 ID、商品与价格快照、付款/交付状态、幂等键、期限 |
| `cdkshop_cdks` | 商品归属、批次、加密 CDK、唯一指纹、库存状态、预留和成交关联 |
| `cdkshop_payments` | 销售订单、商户订单号、渠道配置版本、金额币种、平台流水、支付及退款结果 |
| `cdkshop_payment_channels` | 商城独立易支付配置版本、启用状态、必要商户信息和加密密钥 |
| `cdkshop_sale_events` | 收款、预留、释放、发码、异常、退款和管理操作的审计记录 |
| `cdkshop_reward_tasks` | 已付款登录用户的奖励金额快照、用户 ID、待发/已发/取消状态、操作人、时间和审计信息；不存储或修改中转余额 |

以上为建议命名，实施时按最终迁移规范确定。关键约束包括：

- 商户订单号唯一；同一用户的同一幂等键唯一，改变请求内容后复用键必须拒绝。
- 一枚已售 CDK 只能绑定一笔成功交付的订单；一期一笔订单只能有一枚有效交付 CDK。
- 同一渠道商户的同一平台交易号不能用于确认多个订单。
- 库存状态和关联外键在同一事务中更新；不可只用前端计数或内存锁控制库存。
- 金额以整数分存储，易支付请求使用固定两位十进制字符串；通知金额按十进制精确核对。
- 已付款和已发码状态不能因迟到的未支付通知倒退，退款独立记录，也不清除既有付款事实。

现有易支付统一响应包含浮点金额。商城边界需对原始已验签金额或经过严格校验的十进制结果做精确比较，拒绝非法、非有限、缺失或精度异常的金额，不依赖宽松浮点容差。
商城自行解析其已验签的通知金额并做精确比较，不修改中转 EasyPay 适配器及金额容差逻辑。

## 6. 正常下单和发码

1. 用户提交商品 ID、版本、确认购买信息和幂等键；服务端读取当前售价、渠道和库存。
2. 在短事务中核对营业状态、商品版本、账号状态，以行锁/条件更新预留一枚可售 CDK，创建销售单和支付单。
3. 提交事务后调用易支付。首期一个销售单对应一个商户支付单，重试使用原订单号，不盲目创建多个付款机会。
4. 若网络超时，标记支付创建结果待确认，用原商户订单号查单，不把超时直接视为“平台未创建”。
5. 返回二维码或支付链接；用户端轮询本站持久化状态，查单由后端限速处理。
6. 回调或主动查单获得可信成功结果后，进入同一个幂等收款处理函数。
7. 在事务中锁支付单、销售单和库存，核对金额、商户及有效状态，记录付款并完成唯一发码绑定。
8. 事务提交后返回成功。客户端从受保护接口读取 CDK，显示复制及兑换按钮。

只要库存有效，记录付款和发码绑定尽量在一个短事务中完成。遇到缺货或异常时保留“已付款、交付待处理”的事实，不向用户要求重付。
重试任务处理已付款未发码订单；服务重启后从数据库恢复，不依赖浏览器继续打开或单个进程内存。

## 7. 超时、竞争和异常

库存状态为可售、预留、已售、停用；预留不是已出售，前台可售数量排除预留和停用。
前台库存是展示信息，下单时数据库判断才是最终依据。限制每人未支付订单数量，防止长期占库存。

| 场景 | 处理规则 |
| --- | --- |
| 同时买最后一枚码 | 数据库原子预留，只允许一人成功，其他人提示售罄 |
| 用户重复点击购买 | 幂等键返回同一销售单和同一支付单 |
| 通知与主动查单同时确认 | 走同一个加锁、幂等处理函数，只发一次码 |
| 服务在支付后重启 | 合法回调重试及定时查单恢复处理，已提交结果不重复交付 |
| 浏览器支付返回 | 只展示本站核实结果，不依据返回参数发码 |
| 商品后来改价或下架 | 既有订单按商品和价格快照处理，新订单使用新配置 |
| 暂停商城销售 | 禁止新单，回调、查单、发码重试、历史领取继续工作 |
| 本人关闭页面 | 后端仍处理支付，用户以后可重新查看同一 CDK |
| 发出的码无效 | 由运营核实并留售后/补发记录，不自动回收出售 |

### 不能把付款倒计时等同于支付平台关单

现有 EasyPay 实现没有 `CancelPayment`，所以本站倒计时结束不能保证旧二维码或链接无法继续付款。

到期任务先查单。已支付则正常交付；查单失败或结果不确定则保持待核实，不能把它当作未付款。
确认当时仍未付款后，可以按策略释放预留库存并停止本站支付入口，但必须保留处理晚到付款的能力。
最终释放操作与收款处理锁同一销售单和库存行，避免“查单之后刚到账”导致重复分配。

晚到付款时，若原预留仍有效则交付原码；若已释放，原子分配另一枚同款可售码。
若此时缺货，记录已付款待处理并通知运营补货或退款。不得取走其他订单已预留/已售的码，也不得虚假显示已交付。
上述策略存在短期已付款缺货的可能，需要运营接受；若供应商支付网关支持真正关单，后续可加强为关单成功后释放。

## 8. 退款边界

第一期采用人工审批退款，不开放用户一键自动退款。可以记录退款申请，不能只点按钮就显示退款成功。
若上线直接调用易支付退款，需验证当前平台实际退款和查询协议；结果不明时保留待核实，不自动重复调用。
第一期也可由运营在易支付后台退款，再在本站经过凭证与查单核实后确认，界面明确这是记录外部退款。

- 退款只针对该笔商城支付的金额与交易流水，保留退款状态、处理人和凭证。
- 不调用中转扣余额、撤销订阅或回收充值码的方法。
- 已交付 CDK 默认按已暴露处理，退款不使其自动变为可售。
- 未交付预留码只有确认未暴露、未使用且订单状态满足条件才可释放。
- 本站无法自动判断外站是否兑换，已发码退款及换码需运营核实。

## 9. 旧功能兼容和调整范围

旧 `shop_orders` 人工订单保留，通过“历史人工代购订单”继续查询和处理，原付款链接、记录和权限不变。
新 CDK 商品走新销售接口，新旧订单页面以明确类型区分，不把旧付款完成或交付状态批量转换为新状态。
新页面默认展示 CDK 商品；原人工商品是否继续销售由运营按商品显式配置，不能部署时自动改变。

中转首页推荐区改为指向实际商品；旧宣传设置保留兼容读取，调整文案前可预览。
CDK 付款后为登录用户创建商城本地的待人工发放奖励记录；管理员在线下完成发放后，在代购管理中标记已发并记录操作人/时间。商城绝不自动调用中转余额履约，也不允许访客奖励绑定到登录用户。
产品页明确说明奖励需管理员人工发放；付款和 CDK 交付不等待人工奖励操作。奖励配置、待办和操作历史存于商城数据库；订单后台通过受限管理员 API/身份声明读取，不为此开放中转余额 API 或数据库权限。
现有 `/shop/options` 保留兼容跳转，原外部商城地址仍可配置为次要入口，不替换成供应商兑换入口。

实施范围增加独立 CDK 商城服务/部署清单、独立数据库及受限账号、商城专用 EasyPay 客户端和 API 路由。
共享登录只通过认证端点换取的商城 audience 短时身份令牌衔接；首页入口和中转菜单只加指向 `/shop` 的链接。原充值支付服务、回调、provider registry、支付表结构、倍率、订阅履约和数据库权限不因商城接入而改写。

## 10. 如何证明没有破坏中转

### 代码和数据库约束

商城收款、发码、退款运行在独立进程，不依赖原余额充值、订阅履约或充值码服务，也不导入其实现包。
数据库权限从物理边界阻止越权：商城数据库凭据不能连接中转数据库，中转凭据不能连接商城数据库；商城不存在写入 `users.balance`、订阅、充值兑换码或用量数据的 SQL 通路。
路由测试检查两套 callback 分别路由至各自服务；商城配置和进程不会进入中转 provider registry。
认证测试验证普通 access token 不能直接访问商城 API、商城令牌不能用于中转 API、audience/issuer/签名/权限/过期检查均生效；商城环境拿不到令牌签发私钥和中转 HMAC secret。
代码审查要求现有支付目录、路由和充值/订阅服务在商城功能提交中无改动。若未来必须修改，共享层改动单独提交、单独评审和回归，不与商城上线绑在同一个发布开关内。

### 必须通过的回归矩阵

| 测试 | 验收结果 |
| --- | --- |
| 商城付款并发码 | 库存减少一，订单有一枚 CDK；中转余额、订阅、充值码和用量均未变化 |
| 登录用户奖励记录 | 支付确认后只新增商城待人工奖励记录；中转余额不变，人工标记发放不触发自动入账 |
| 访客购买 | 可支付并领取 CDK；不关联本站用户、不产生可发放中转余额奖励 |
| 中转余额充值 | 按原金额/倍率到账；商城库存、销售订单和发码记录均未变化 |
| 中转购买订阅 | 按原规则开通；商城数据均未变化 |
| 双向回调串线及伪造通知 | 未授权的余额/订阅/库存均不变化，错误可追踪 |
| 商城退款 | 只更新商城退款及对应支付记录，中转权益不变化 |
| 并发、重复回调和查单 | 同一枚 CDK 不会交给两人，同一订单不会拿两枚码 |
| 到期释放与付款竞争 | 付款事实保留，库存绑定不冲突，缺货有明确待处理状态 |
| 商城开关与渠道配置变更 | 原中转下单、回调和订阅处理保持可用；旧商城订单可继续处理 |
| 登录及权限 | 商品可公开看；订单和 CDK 仅本人/授权管理员可读，普通用户无法管理库存 |
| 进程重启、支付超时、数据库失败 | 不漏掉已付款订单、不重复支付或发码，可通过持久化记录恢复 |
| 商城进程崩溃/资源打满 | 只触发商城健康告警和熔断；中转健康检查、充值与订阅仍成功 |
| 商城数据库凭据越权测试 | 商城凭据访问中转库及中转凭据访问商城库均被数据库拒绝 |

以上使用隔离的测试数据库、受限数据库账号和可控模拟支付接口覆盖，并对中转服务可用性及余额/订阅/库存的前后值作实际断言，不只检查 HTTP 200。
商城协议测试验证独立 EasyPay 客户端；中转现有 `internal/service` 支付/充值/订阅、`internal/payment/provider` 测试作为未修改基线运行，商城实现不需改动这些共享目录。
桌面和手机验证浏览、登录返回、付款、领取、复制和外站跳转，不在测试中兑换真实生产 CDK。

## 11. 实施及上线顺序

1. 建立独立服务、数据库/凭据、密钥和健康/资源边界；先做中转隔离与回归验证。
2. 完成商品、CDK 库存和管理后台，使用测试码验证库存预留和去重。
3. 在商城服务实现独立易支付客户端、下单、回调、查单、迟到付款和唯一发码，执行隔离测试。
4. 完成独立商城布局、支付和交付页面、首页入口与旧订单兼容。
5. 部署到公网可回调环境，独立配置同一商户的必要参数，核对商城与充值使用不同的业务回调地址。
6. 在明确金额和测试商品的范围内做一笔真实小额支付验收，并确认原中转未改代码、不中断且充值/订阅仍成功。
7. 确认对账和异常订单处理入口可用后，小范围开放销售，观察再扩大。

新增迁移不改旧迁移，不删除原表。上线前备份数据库和所需加密密钥。
发生问题优先关闭商城新销售，继续处理已付款订单。不能直接退回不支持新销售的旧二进制而丢掉回调和发码处理能力。
只有在途支付、待交付和退款事项清理完成，或有兼容接收措施后，才能进行涉及新商城逻辑的版本回退。

## 12. 第一期完成标准

运营可录商品和 CDK，前台库存真实可用；用户登录付款后只能领取自己的唯一 CDK，并能跳转供应商兑换。
支付关闭、超时、重试、服务重启和库存竞争都有明确可恢复行为。
原中转的余额充值、订阅、充值兑换码、API 计费和权限通过回归，隔离测试证明确无越界数据写入。
本站经营记录完整保留到已发码、退款或异常待处理，不承担外站兑换完成状态的同步职责。
